# 开源项目对标改进七步法（Benchmark Playbook）

> 核心理念：**当某一检索能力或工程模块反复踩坑时，不要拍脑袋闭门造车。先找该领域高星但仍活跃的成熟项目与已归档反面教材，对照真实源码与社区 Issue，做减法式借鉴。**

---

## 一、七步执行流程

| 步 | 动作 | 交付物 | 常见误区 |
| --: | :--- | :--- | :--- |
| 1 | **圈定范围**：列出当前工作流真实用到的模块、场景与关键链路 | 现状覆盖清单 | 只盯着报错模块，漏掉未接通的空白场景 |
| 2 | **双向选标**：每个方向选 1 个活跃高星项目 + 1 个已归档或失败项目作反例 | 对标候选列表 | 只看 Star 数排名，把停更老项目当宝 |
| 3 | **三维验尸**：查最近真实代码 Commit、未关 Issue 响应率、是否归档或大版本断代 | 每项目一行体检结论 | 把改 README 算活跃；忽略 `v2` 彻底不兼容重写的坑 |
| 4 | **精读关键文件**：只读架构核心层（异常隔离 / 限流退避 / 状态模型 / 接口契约） | 源码机制摘要 | 一头扎进无关业务 UI 细节，迷失方向 |
| 5 | **审视 Issue 与退坑贴**：重点搜 `deprecated / pitfall / memory leak / broke / API cost` 等反馈 | Issue 编号与原话 | 只看项目自吹的亮点文档，不看长期运行痛点 |
| 6 | **列“抄什么 / 绝对不抄什么”**：写清收益、改造点、验收断言与拒绝引入的重依赖 | 性价比排序清单 | 为了一个函数引入一整套重型框架 |
| 7 | **先离线单测后端到端**：先补 `unittest` 断言再做一次真实回归，并沉淀进评估集 | 测试通过记录 + eval 用例 | 改完不验证，下次迭代悄悄回退到老 bug |

## 二、四条基准铁律

1. **工具异常显式透传**：网络超时、限流、认证失败或版本API错误必须原样写明受阻环节，严禁把失败静音后写成“社区零负面反馈”。
2. **三维验尸不及格只作反面教材**：凡已正式 `archived`、超 365 天无真实代码提交或处于频繁 Breaking Rewrite 期的项目，**只吸取架构教训，绝不引入运行时依赖**。
3. **实体纯血度防错配**：跨分支、跨大版本（如 v1 vs v2 完全重写）、跨硬件架构（如 x86 vs ARM 容器）的 Issue 结论严禁混为一谈，必须带 `[年份 | 独立信源数]` 与四档定性（🟢/🔴/🟡/❓）。
4. **只借鉴思路，严控依赖膨胀**：核验逻辑与核心数据契约尽量保持纯标准库、零重框架绑定，确保 5 年后依然一行 Python 直接可跑。

## 三、单条改进的证据记录模板

```text
- 对标项目：owner/repo（Stars / 最后真实 Commit / 是否归档 / 开源协议）
- 机制源码：<文件路径> 中的 <关键函数或设计模式>
- 社区 Issue / 反馈：#<Issue编号> 核心反馈 + 原始 URL（含时间、互动度）
- 我们的现状：现有流程/脚本差在哪里
- 改造动作：改哪个文件 + 用哪条离线单测验收 + 潜在风险
- 证据定性：🟢/🔴/🟡/❓ [YYYY | 独立信源数]
```

## 四、对标评估报告输出契约

完整评估报告必须包含六项核心组件：
1. 覆盖现状与缺口清单（标明本次实际触达的通道与未触达盲区）；
2. 「确定借鉴」vs「明确放弃」双栏对比表；
3. 按实施性价比排序的改造方案；
4. 反面教材清单与过程中遇到的工具/网络异常日志；
5. 待后续验证的假设边界；
6. 1~2 条精选一手审计证据（含时间、作者、互动数据、原始链接与关键原话）。
